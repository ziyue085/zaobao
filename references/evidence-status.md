# evidence_status 详解

每条候选在内部必须有一个 `evidence_status`。它是"这条信息凭什么可信"的答案，
不是"这条信息好不好"的评价。

## 一、五个取值

| 取值 | 定义 | 能否输出 | 是否必须披露 |
|---|---|---|---|
| `VERIFIED_PRIMARY` | 找到一手来源 | 可以 | 否 |
| `VERIFIED_CROSS_SOURCE` | 没有一手来源，但至少两家独立可信来源互证 | 可以 | 否 |
| `SECONDARY_ONLY` | 只有可信二手报道 | 重要时可以 | **必须标「尚未见一手确认」** |
| `UNVERIFIED` | 来源不足 | 仅限「意外但重要」，且极少量 | **必须标「待核实」** |
| `REJECTED` | 证据不可用 | 不可以 | — |

## 二、"一手"到底指什么

判据只有一条：**发布者是不是这件事的主体本身。**

| 场景 | 层级 | 理由 |
|---|---|---|
| 公司官网发布年报 | primary | 主体自己发的 |
| 记者报道这家公司发了年报 | trusted_secondary | 主体是记者所在的媒体 |
| 交易所披露该公司公告 | primary | 交易所是法定披露渠道 |
| 政府网站发布规章 | primary | 主体自己发的 |
| 新闻媒体转述规章 | trusted_secondary | 转述 |
| 论文作者在 arXiv 贴出预印本 | primary | 作者原文 |
| 媒体报道这篇论文 | trusted_secondary | 转述（也可能是错误转述） |
| 公司 CEO 在自己的认证账号发言 | primary | 发布账号即当事人 |
| 网友转发 CEO 的话 | discovery_only | 不是当事人 |

## 三、"多源互证"的两个陷阱

### 陷阱一：同源多平台

同一家媒体集团旗下的报纸、网站、客户端、公众号，**算一家**。
一篇通稿被十家媒体转载，**不是十家互证**，是转载。

判断方法：看内容和措辞是不是完全一样。措辞完全一致 → 同一稿源。

### 陷阱二：社交平台的级联

A 发帖 → B 转发 → C 引用 B。看起来"有多个来源"，实际上是同一条信息在扩散。

社交平台只有在发帖者是当事人时才升级为一手；否则一律 `discovery_only`。

## 四、三种特殊情形

### 1. 准一手（quasi-primary）

新华社、央视、人民日报对**中央文件、国务院文件**的发布，实际操作中常常就是首发渠道。
这类来源用于普适性政策时可以视为准一手，但：

- 不得静默升级为 `primary`
- 系统会留一条 INFO 记录 `QUASI_PRIMARY_USED`
- 有条件时应回政府网站补一手链接

### 2. 公司官网不在已知清单里

`config/sources.yaml` 不可能枚举所有公司官网。遇到清单之外的域名：

- 如果它确实是公司官方站：标 `tier: primary` + `is_first_party: true` + 写清 `tier_reason`
- 如果说不清：按已知层级判，宁可判低

系统对这种情况会强制要求 `is_first_party` 与 `tier_reason` 同时存在，否则判 BLOCK。

### 3. 把社交平台声明为一手

只有当发布账号就是当事人／官方账号／负责人／论文作者时才允许。
系统会保留一条 WARN `DISCOVERY_DOMAIN_AS_PRIMARY` 提醒复查 —— 这是设计上的"留痕"，不是错误。

## 五、分级的实际意义

`evidence_status` 同时决定三件事：

1. **能不能发**（REJECTED 直接丢弃）
2. **发的时候要不要加标注**（SECONDARY_ONLY / UNVERIFIED 必须加）
3. **能不能进特定栏目**（UNVERIFIED 只能进「意外但重要」）

所以它不是标签，是闸门。

## 六、判定时的默认倾向

**判低不判高。**

- 判高了：用户在微信里读到一条不实信息，代价由用户承担。
- 判低了：少发一条，用户不会因此受损。

拿不准的时候，降一级。降级只影响披露标记，不影响已经确认的事实。
