# 设计说明

记录三类东西：**取舍**（为什么这么做）、**依据**（阈值从哪来）、**限制**（做不到什么）。

## 一、第一原则：规则要分"可判定"与"不可判定"

收到一份长规则清单时，第一件事是逐条问：**这条规则可判定吗？**

| 可判定（→ 写成代码） | 不可判定（→ 留在文档与提示词） |
|---|---|
| 字段是否缺失（含三态缺席） | 这条新闻重不重要 |
| 时间是否落在 24 小时窗口内 | 提问与叙述的语气是否合适 |
| fingerprint 是否与历史／本期重复 | 摘要是否忠实转述了原文 |
| 枚举是否合法 | 「实质新进展」的语义判断（只能按枚举近似） |
| 计数是否越界（Top ≤ 3 等） | 来源是否"真的"可靠（只能按域名与第一方标记判） |
| 字面违规（标题党词表、表格、搜索 URL） | 标题是否"真的"直接表达了事实 |

经验比例：规则密集型项目约 40—60% 的规则可判定。**这部分必须进脚本**。
否则规则会随会话随机失效，而且没有任何机制会发现。

本项目 83 个 code 中，约六成属于第一列。

## 二、规则冲突与裁决

### 冲突 1：`UPDATED` 能不能输出

- 规范第十二节：「只有 **PASS** 状态可以进入最终输出。」
- 规范测试 Case 4：「3 天前事件今天发布正式调查结果 → **UPDATED**，可以输出新进展。」

两句话直接冲突：如果只有 PASS 能输出，UPDATED 就永远发不出去，Case 4 无法满足。

**裁决**：把 `PASS` 与 `UPDATED` 都定义为"可输出终态"，语义区分开 ——

- `PASS` = 本期（24 小时内）发生的新事件
- `UPDATED` = 对历史事件的实质新进展

其余四个状态（`OLD` / `DUPLICATE` / `UNVERIFIED` / `LOW_VALUE`）一律不可输出。

理由：Case 4 描述的是**它允许输出**，而第十二节的"只有 PASS"更可能是在强调
"发现 ≠ 发送"这个意思（即"不是所有候选都能发"），而不是在禁止 UPDATED。
两者取交集会让 Case 4 变成死规则。

实现：`scripts/zaobao_check.py: OUTPUT_STATUSES = ("PASS", "UPDATED")`。
这是唯一一处对原始规范的**实质性放宽**，需要在以后的需求评审中确认。

### 冲突 2：披露标记对谁生效

规范要求 SECONDARY_ONLY 必须标「尚未见一手确认」。但如果对**全部候选**执行，一个
已经被判 `LOW_VALUE` 的候选也会因为没写披露标记而报 BLOCK。

**裁决**：区分两类缺陷 ——

- **结构性缺陷**（URL 不合法、搜索引擎当来源、层级无法自证、栏目被排除、标题党、
  建议／分析泄漏、fingerprint 不完整、时间字段缺失）→ **任何时候都 BLOCK**
- **证据充分性缺陷**（来源不够互证、缺披露、primary_url 缺失、只有社交平台作来源、
  栏目准入门槛不满足）→ **只有该条真的进入输出时才 BLOCK，否则降为 INFO**

理由：一份 30 条候选的清单会产生上百条无关阻断，真正的问题会被淹没。
实现：`_sev_for_status()`。

## 三、时间窗的参照点

规范给了一批"允许进入窗口"的例外（首次官方确认、新公告、正式文件、新数据、
新处罚判决、调查结果、产品上线、传闻被证实或证伪）。

实现上把它们建模成两个字段：

```
new_progress_at    = 新进展发生时间
new_progress_type  = 新进展属于哪一类（枚举）
```

**两个必须同时具备**才算实质新进展。只填时间不填类型 → 不允许升级为 `UPDATED`。

理由：只填时间说明还没想清楚"这到底算不算新进展"。这是
「未检查 ≠ 已通过」在时间维度的应用。

## 四、去重：为什么用 fingerprint 而不是标题

标题是媒体加工的产物。同一件事会被写成：

```
中芯国际发布2026年三季度报告
中芯国际三季报出炉，营收同比增长12%
SMIC 三季度业绩披露
```

按标题判重，四条会被当成四件事。

所以 fingerprint 只用**主体 + 核心动作 + 核心事件**，且主语先做别名归并：

```
中芯国际#发布#2026年三季度报告
```

`object` 的粒度是唯一需要拿捏的地方：

- 太细（带上具体数值）→ 数值微调就匹配不上
- 太粗（只写"财报"）→ 不同年份的财报被判成同一件

取法：**带年份与期次，不带具体数字**。

别名表放在 `config/watchlist.yaml: aliases`，因为这是最容易变化的部分。

## 五、阈值与依据

| 常量 | 取值 | 依据 |
|---|---|---|
| `WINDOW_HOURS` | 24 | 规范明确给定 |
| `HISTORY_DEDUP_DAYS` | 30 | 规范要求"至少 7 天"；取 30 天是为了覆盖月度周期事件 |
| `HISTORY_MIN_DAYS` | 7 | 规范下限 |
| `UNEXPECTED_MAX_PER_DAY` | 3 | 规范明确给定 |
| `TOP_PICK_MAX` | 3 | 规范明确给定 |
| `ISSUE_MAX_ITEMS` | 12 | 规范给的常态上限（5—12） |
| `TITLE_MAX_CHARS` | 45 | **经验取值**。微信一行约 18 个汉字，45 字约 2.5 行 |
| `TITLE_MIN_CHARS` | 6 | **经验取值**。低于 6 字基本没说明事实 |
| `BODY_MAX_FACTS` | 3 | 规范明确给定（1—3 句） |

**除规范给定的之外，其余都是经验取值，不是统计结论。** 觉得不合适就改，改完重跑测试。

## 六、为什么不用数据库

规范明确要求不引入数据库服务器、Docker、Redis、向量库。

跨日去重的状态就是一份 JSONL：一行一条，追加写，用文本工具就能看。
`record` 与 `prune` 两个子命令覆盖了写入与裁减的全部需求。

代价：并发写不安全、查询靠全表扫描。以"每天跑一次、保留 30 天、几十条"的规模，
这两点都不构成问题。**等到真的成为问题时再换，现在换是过度工程。**

结构化校验用 JSON Schema 文件（`schemas/`），是给人和模型看的契约，
不是运行时依赖 —— 规则层自己做了等价的关键字段校验，因此零依赖即可运行。

## 七、为什么把渲染也写成脚本

渲染本来可以完全交给模型。写成脚本的理由：

1. **格式合规可以被验证。** 表格、来源行格式、栏目顺序、Top 条数，全都能确定性检查。
2. **渲染器可以自带闸门。** 渲染前后各跑一次检查，有 BLOCK 就拒绝写文件。
   这让"不要绕过去"从一个纪律变成一道机制。
3. **减少模型自由度。** 能搬的就不让它写。

代价：格式调整需要改代码。以当前格式的稳定程度，这个代价可以接受。

## 八、零依赖的代价

`mini_yaml_load()` 是一个手写的 YAML 子集解析器，只支持本项目配置文件用到的结构：

- 支持：缩进嵌套映射、`- ` 序列、`- key: value` 起始的内联映射及续行、
  内联 `[a, b]` 与 `{a: b}`、`#` 注释、单双引号
- 不支持：锚点与别名、多行标量（`|` / `>`）、复杂键、多文档

**它正确性由测试保证**：`tests/run_cli_smoke.py` 断言它与 PyYAML 对两个配置文件的
解析结果**完全相等**。PyYAML 不存在时才走这条路。

如果你要往配置里加锚点或多行文本，先装 PyYAML，或者先扩展这个解析器并补测试。

## 九、已知限制（摘要）

完整版在 `references/reliability-gaps.md`。最要紧的三条：

1. **重要性判断仍然依赖模型，而且是当前最大的一处残留依赖。**
   `has_material_event` 已被 `material_update` 事实块取代（见第十一节），
   但"这件事值不值得占版面"没有可判定形式 —— 程序只能要求留下 `importance_reason`。
   实测 23 条产出里 5 条误收，全部属于这一类。
2. **词表是穷举式的。** 新出现的标题党词、新的"分析味"表述不会自动被拦。
   需要每周人工回看并补充。
3. **域名清单不可能完备。** 清单外的域名要人工判级并写进 `tier_reason`。
   规则层只能保证"说不清理由的一手声明会被拦下"，不能保证"判对了"。

## 十、变更纪律

改规则时：

1. 改 `scripts/zaobao_check.py`（新增 code 时用新的、稳定的名字）
2. 在 `tests/cases/` 加夹具：**一个规则对应一个夹具，且必须包含"触发"与"修正后不触发"两个 step**
3. 在 `tests/mutate.py` 加一条对应的变异，证明新规则被测试真正覆盖
4. 跑四段：`run_regression` → `run_cli_smoke` → `mutate` → `check_output_readability`
5. 更新本文与 `tests/test-cases.md` 的对照表

**只改第 1 步就提交，等于把规则变成一句没人验证的话。**

### 关于阈值冲突

两处标题长度上限并存，是有意的，但需要知道：

| 位置 | 值 | 用途 |
|---|---|---|
| `zaobao_check.py: TITLE_MAX_CHARS` | 45 | **硬闸门**。超过即 BLOCK，防的是"把一段话当标题" |
| `check_output_readability.py: MAX_TITLE` | 30 | **可读性指标**。超过只报 FAIL，不阻断发布 |

两者不合并，因为一个是"不能发"、一个是"发出去不好读"。
v0.1.1 收尾时，9 期实测曾有 1 期落在 30—45 字之间（`round-05`，31 字）：闸门放行、可读性不通过。
处理方式是把**那一条标题压回 30 字以内**（31 → 24 字，事实与含义不变），而不是调 `MAX_TITLE`；
现在 9 期全过，两处阈值仍分别是 45 与 30。

## 十一、v0.1.1 的架构变更

### 为什么改

v0.1.0 把三件事都交给了模型：一是我查过了没有（`*_checked`），二是有没有实质事件（`has_material_event`），
三是这个来源算不算一手（`sources[].tier`）。程序只能检查「声明与清单是否自洽」——
**判定主体仍然是模型**。83 个零散 rule code 平铺在一起，也没人能从顶层读懂放行逻辑。

### 改成了什么

**一句话原则：能由程序根据原始字段计算的判断，不允许继续依赖模型自报。**

- 候选保存**可审计事实**，不保存结论：
  `published_at` / `material_update{claim,published_at,source_url}` / `new_progress_at` / `watchlist_subject`。
- 由程序推出派生状态（`derive()`）：
  `is_within_24h` / `has_primary_source` / `verification_source_count` / `has_cross_source_verification` /
  `history_match` / `is_material_update` / `is_output_eligible`。
- 规则收敛为**七个顶层 Gate**：`structure / freshness / evidence / duplication / importance / category / output`。
  rule code 退化为 Gate 内部的诊断信息，顶层读代码从 `run_*_gate()` 开始。
- 来源判定改为**正向证据优先**（`scripts/zaobao_classify.py`）：
  先问"是不是原始发布者"，再问"是不是政府 / 监管 / 交易所"，再问"是不是官方公告 / 官方博客 / GitHub / 论文原文"，
  最后才落到"有没有可靠独立来源交叉确认"。黑名单只用于排除搜索结果页与内容农场。
- 清单外的域名仍有人工通道：`is_first_party + tier_reason` 可补证为一手，
  `tier: trusted_secondary + tier_reason` 可补证为可信二手 —— 两条通道都要留下理由，且都会记 INFO。

### 刻意保留的两处模型判断

1. **重要性**：不可判定，所以保留模型判断，但要求留下 `importance_reason`，而不是一个 `important=true`。
2. **栏目归类**：同上。程序只校验栏目是否在 watchlist 的 priority 里，不判断归得对不对。

这就是为什么实战评估里仍然出现「事实没问题但不该占版面」的误收 ——
那不是 Gate 失守，而是这两处本来就留给人的地方。详见 `docs/evaluation.md`。

### 用实战评估代替覆盖率当 KPI

模块覆盖率再高也回答不了「这份早报读起来行不行」。所以 v0.1.1 加了 `tests/evals/`：
真实窗口、真实来源、正常走完整 Gate、逐条人工打标签，最后看误收 / 漏收 / 旧闻 / 重复 / 来源可靠性。
**架构更漂亮但真实早报没有变好，不算 PASS。**
